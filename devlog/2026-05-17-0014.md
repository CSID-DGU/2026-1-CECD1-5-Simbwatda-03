## 1. Phase 1a — OVSeg3R IBSp 구현

### 1.1 정신 vs REACT3D 매핑
OVSeg3R IBSp 원본 (KNN graph + 2D mask 경계에서 edge 삭제) → REACT3D는 Louvain on face co-occurrence graph라 직접 적용 못 함. 정신만 가져와서:
- 같은 view 안에서 **서로 다른 2D mask에 속하는 face pair**의 edge에 **separation penalty** 누적
- 임계값 비교 시 `net = same_count - λ * diff_count` 사용

### 1.2 코드 변경 (`scene2part/s2p_1_fast.py`)
- 백업: `s2p_1_fast.py.fun3du_only`
- `--ibsp_lambda` CLI 인자 추가 (기본 1.0)
- `faces_idxs_per_mask`에 `frame_idx` 추가 — 같은 frame mask group identify용
- 1차 pass 후 separation matrix 구축:
  - frame별로 face → mask_idx hash 생성 (first-mask-wins)
  - 같은 frame의 visible faces로 edge_count_matrix 부분 행렬 추출
  - `mu != mv`인 face pair에 weight `(w_view_A + w_view_B)/2` 누적
- 임계값 비교에서 `net = counts - args.ibsp_lambda * sep_counts`

### 1.3 OVSeg3R 원본 코드 검증 시도 — **코드 비공개**
- arXiv 2509.23541, 검색 결과 GitHub repo 없음 (paper text만)
- 알고리즘 텍스트 (Algorithm 1: 2D Instance Boundary-aware Superpoint Graph) 만 보고 구현
- 정신만 따랐고 KNN graph가 아닌 face co-occurrence라 변형 필요

### 1.4 Fun3DU 원본 코드 확인 — **우리 구현과 다름**
- `/tmp/fun3du/utils/io.py`: `choosen_score = 0.5*(mask_score + owl_score)` → `np.argsort(-choosen_score)[:n_samples]` — **top-K view selection** 방식 (hard filter)
- 우리 구현: 모든 view를 `w_view = exp(-(arc_kl + mod_kl))`로 곱해서 누적 — **soft weighting**
- → 정신은 같지만 메커니즘 다름. devlog에서 "Phase 1c top-K voting"이라 부른 게 사실 원본 방식.

### 1.5 실행 + 결과
tmux `s2p_ibsp`로 s2p_1~6 재실행:
- per-mask weight: mean=0.1087, median=0.0581 (Fun3DU만 때와 유사)
- effective_threshold = 0.326
- **IBSp separation events: 109,816,729** (1억 건의 cross-mask 동시발생 감지)
- sep_matrix nnz: 22.7M
- **Raw mesh: 49개** (Fun3DU만 47, 옛 REACT3D 61)

### 1.6 part-to-interactive 결과
- 49 raw → OPDM → **13 articulated 후보** (Fun3DU만 24!)
- IoU>0.5 dedup: **1쌍만 제거** (mesh_307×mesh_077, IoU 0.59) — Fun3DU만 때 12쌍 (.999 IoU)
- **최종 12 articulated parts**

### 1.7 OBB tilt 비교 — IBSp 효과 확인
| 지표 | Fun3DU only | **Fun3DU + IBSp** |
|------|-------------|-------------------|
| 최대 revolute OBB tilt | 3.50° (mesh_055) | **1.32°** (mesh_518) |
| 1° 이상 revolute 수 | 4 | 2 |

## 3. Root cause 진단 (`/tmp/diag_overlap.py`)

### 3.1 진단 스크립트 — pairwise AABB overlap volume
- 12 part × 66 pair × 4 component (part, OBB, base, inner)
- 결과 충격:

| Component | overlap total (66쌍) | overlap > 0 pair 수 |
|-----------|----------------------|---------------------|
| part.ply | 0.007 m³ | 6 |
| OBB | 0.010 m³ | 6 |
| **base.obj** | **0.156 m³** | **6** |
| inner_box.obj | **0.000** | **0** (전부 없음) |

- base.obj가 OBB보다 **13배 큰 부피로 겹침**
- rotation type은 **inner_box.obj 아예 안 만들어짐** (우리가 이전에 막은 거)

### 3.2 base.obj가 왜 그렇게 큰가
- `inference.py:902`: `box_mesh, inner_box_mesh = corners_to_mesh(cuboid_world, pred_type)`
- **OBB가 아니라 `cuboid_world`로 만든다!**
- `cuboid_world.npy` 주석: "depth-completed cuboid"

### 3.3 OBB vs cuboid_world 비교
| mesh | OBB Y두께 | cuboid_world Y두께 | 배율 |
|------|----------|--------------|------|
| mesh_518 | 5cm | **66cm** | **14.6x** |
| mesh_519 | 5cm | **67cm** | **13.5x** |
| mesh_077 | 4cm | 49cm | 11.3x |
| mesh_049 | 4cm | 46cm | 10.6x |

- mesh_518/519 part 중심 거리 **59.6cm**, 각자 cuboid 깊이 66/67cm
- → 캐비닛 공유하는 인접 part들의 cuboid가 깊이 방향으로 만나서 겹침
- **mask bleeding과 무관. cuboid_world (OPDM 깊이 예측) 그 자체가 원인.**

## 7. cuboid_world 생성 로직 추적

`visualization.py:1401-1527` `complete_point_cloud_true_mesh`:

1. mask_points로 OBB 계산 (line 1415)
2. OBB의 두 긴 edge → v1, v2 (line 1437-1440)
3. `face_normal = cross(v1, v2)` (line 1443)
4. obb_x = v1/norm, obb_y = cross(normal, x), obb_normal = face_normal (직교 좌표, line 1452-1456)
5. **scene_pcd에 raycast** (`get_deepest_in_direction`, line 1465) → first hit = `proj_max`
6. `proj_min, proj_max = np.min(projections_mask), np.max(projections_mask)` from mask, then `proj_max = min(proj_max, first_hit)`
7. cuboid corners = OBB의 xy 범위 × [proj_min, proj_max] (line 1507-1516)

### 7.1 비틀어짐 원인 정리
- **frame은 OBB axes 사용 → 이론상 OBB와 정렬**
- 그러나 **OBB 자체가 mask 노이즈로 1~1.32° 비틀어짐** (IBSp 후 잔존) → cuboid도 같이 비틀어짐
- `proj_min`: mask의 가장 inner-extruded 값 — mask 노이즈에 의한 표면에서 떨어진 inner 점이면 cuboid 시작이 표면 뒤가 아니라 떨어진 곳
- `proj_max`: raycast first hit — 인접 객체나 잘못된 surface hit하면 이상한 깊이

### 7.2 논문에 cuboid 보정 있나?
- Section III-C "Articulation refinement"의 refinement는 **axis만** 보정:
  - prismatic: axis ← OBB front-face normal
  - revolute: axis ← OBB principal edge
- **cuboid는 보정 안 함.** corner 위치는 mask 노이즈 + scene raycast에 의존 — 노이즈 그대로.

## 12. 학습/메모

- **cuboid_world는 OPDM 결과물의 노이즈가 모이는 지점.** axis는 refinement 받지만 cuboid는 raw. 캐비닛 깊이가 OBB 두께의 10~15배까지 부풀려질 수 있고 그게 base 겹침의 진짜 원인.
- **vis_interactive와 URDF는 다른 path로 mesh 로드.** URDF gen 변경이 시각화에 자동 반영 안 됨. vis_interactive 따로 봐야 함.
- **per-part 독립 geometry 합성은 한계.** 인접 part 정보 없으면 같은 캐비닛 깊이 두 번 점유.
- **OVSeg3R 코드 비공개, Fun3DU 우리 구현은 원본과 다른 방식.** 정신만 따라했지만 실제 메커니즘 차이는 명시해두자.
